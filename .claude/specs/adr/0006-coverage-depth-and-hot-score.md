# ADR-0006: 커버리지는 표본 깊이로, 신생 랭킹은 속도 점수로

- **날짜**: 2026-07-30
- **상태**: 승인됨
- **관련 기능**: trend-ranking-v2 ([ADR-0005](0005-trend-slice-and-velocity.md) 후속)

## 맥락

trend-discovery(v1, ADR-0005) 배포 후 실사용에서 두 가지가 드러났다.
1. 1주일에 2만 스타를 받은 레포가 대시보드에 아예 안 뜬다 — 스타 절대 상위 30개(`ETL_PER_QUERY=30`) 표본에 못 들면 수집·추적 자체가 안 된다.
2. 신생 급상승이 "예전 큰 레포 숫자만 갱신"되는 느낌 — 90일 창 + 절대 델타 순이라 이미 큰 신생이 상위를 독점한다.

GitHub Search API에는 "기간 내 스타 증가순" 정렬이 없다(공식 REST 한계). 따라서 "지금 뜨는 것"을 직접 질의할 수 없다.

## 검토한 대안

### 커버리지(폭발 레포 포착)
1. **수집 깊이 확대 (per_page 30→100)** — 장점: `per_page` 상한이 100이라 단일 요청으로 표본 3배, API 비용 사실상 불변. 2만 스타면 대부분 상위 100 내. 단점: 초거대 니치(100위 밖)는 여전히 놓침, 저장량 증가.
2. **페이지네이션으로 200+ 확대** — 장점: 더 확실. 단점: 요청 수 2배+, 레이트리밋(30/min) 압박, 복잡도.
3. **활동순(`sort=updated`/`pushed:>`) 슬라이스 추가** — 장점: 활발한 레포 포착. 단점: 활동 ≠ 스타 급증, 노이즈.
4. **GitHub Trending 스크래핑** — 정확하지만 비공식·파손 위험·키워드 필터 불가로 제품 컨셉과 불일치.

### 신생 랭킹
1. **창 30일 + 속도 `delta/age`** — 최신성(작은 분모)과 최근 증가를 동시 반영. 어린 폭발이 상위.
2. **창 30일 + 절대 델타** — 여전히 큰 신생 편향.
3. **창 90일 유지 + 점수 변경** — "진짜 최신" 강조 약함.

## 결정

- **커버리지**: 대안 1(**깊이 100**). 비용이 거의 없고 대부분의 급상승을 포착. 초거대 니치 한계는 감수(Non-goal). "오래됐지만 폭발" 레포는 표본 진입 후 Top Movers(성장률 %순)로 노출된다 — 신생이 아니므로 신생 급상승에는 넣지 않는다.
- **신생 랭킹**: 대안 1(**창 30일 + 속도 `star_delta / max(age_days,1)`**). 수집 창(90일)과 노출 창(30일)을 분리해, 30~90일 레포도 추적은 하되 신생 급상승 표시에서만 제외한다.
- **정체 숨김**: 조회 시 `star_delta > 0` 필터. 절대 임계값(>=N)은 니치 규모 편차 때문에 부적절 — "움직임 있음"이 규모 무관하게 공정.

## 결과

- 급상승 레포가 표본에 들어와 추적·노출된다. 저장량은 사용자·검색어당 최대 100행/슬라이스로 증가(수용 가능).
- 신생 급상승이 "어리고 지금 크는" 레포로 채워지고, 정체 레포는 목록에서 사라진다.
- 여전히 첫 수집(delta=0)엔 정체 필터로 잠깐 제외 → 2회차부터 노출(의도된 동작).
- 100위 밖의 급상승을 놓치는 경우가 남으면, 페이지네이션(대안 2) 또는 별도 축(대안 3)을 재검토한다.
- ADR-0005의 velocity(평생 평균, 조회 시 계산) 결정은 유지 — 이번엔 그 식을 신생 급상승 "순위"로 계속 쓰되 창을 30일로 좁히고 정체 필터를 더한 것.
